# BassClass: working notes for Claude

## Git workflow (always)

- Repository: https://github.com/josich/BassClass (remote `origin`, branch `main`).
- **Push every change.** After finishing any change (code, content, docs, assets): verify it, then commit and push to `origin main` in the same turn. Never leave work uncommitted or unpushed.
- The commit identity is already set locally in this repo (`josich` / `76693732+josich@users.noreply.github.com`). Don't change it or set a global one.
- End every commit message with the `Co-Authored-By` trailer from the session's attribution instructions.
- Windows PowerShell: write multi-line commit messages to a temp file and use `git commit -F <file>`. Here-strings are not passed to stdin.
- Order: `git add -A` → `git commit` → `git pull --rebase origin main` → `git push origin main`. The pull must come after the commit (rebase refuses unstaged changes). CI can push commits too: it committed the signing key `android/app/bassclass.p12` on its first run.
- Each push to `main` runs two GitHub Actions workflows:
  - **Build Android APK:** builds a signed release APK and publishes GitHub Release `v1.0.<run number>`. The user installs from https://github.com/josich/BassClass/releases/latest/download/BassClass.apk. Never delete or replace `bassclass.p12`: updates would stop installing over the old version.
  - **Publish web app (GitHub Pages):** deploys `web/` to https://josich.github.io/BassClass/, only once Pages → Source is "GitHub Actions"; until then it skips.
- Commits that change nothing in the app (QA reports, notes) end their first line with `[skip ci]` so no identical APK release is published.
- After pushing, check the runs at `https://api.github.com/repos/josich/BassClass/actions/runs` and fix any failure before reporting the work as done.
- Tell the user after every push, once the runs have finished: the commit, that CI passed, and the build version, `v1.0.<run_number>` of the "Build Android APK" run (user, 2026-10-21). A `[skip ci]` commit has no build: say so.

## Before committing

1. Start the dev server: `python tools/serve.py`, or the `bassclass` launch config. It serves `web/` on http://localhost:8765.
2. In the page console run `(await import('/js/selftest.js')).run()`. It must report `problems: 0`. It builds every exercise on 4/5/6-string basses and checks every note.
3. If exercises were added or changed, regenerate the catalogue: `(await import('/js/selftest.js')).saveCatalogue()` → `docs/CATALOGUE.md`.
4. Check UI changes visually in the browser pane at a landscape phone size (e.g. 800×380).

## Project facts

- `web/` is the whole app: static ES modules, no build step. `android/` wraps it in a WebView (`assets.srcDirs("../../web")`).
- This PC has no JDK, Android SDK, Node, Gradle or numpy, so APKs are built only by GitHub Actions. Audio processing runs in the browser (`web/js/dev/sampleprep.js`).
- Exercises live in `web/js/curriculum/`, one file per module, with shared helpers in `common.js`. See README "Adding an exercise".
- The guided Course (user, 2026-10-20) lives in `web/js/course/`: `data.js` (the format and the flattened view; each stage in `stages/s<N>.js`: units → lessons → steps; a step = exercise id + preset options `p` + `from`/`goal` tempo), `progress.js` (localStorage `bassclass.course.v1`), and `web/js/ui/course.js` (Home block, `#/course`, `#/course/<lesson>`, `#/course/placement`). An exercise opened from a lesson carries `ls=<lesson>.<step>` (and `demo=1` for "Hear it", `rv=1` for a review). Lesson ids are stored: never rename one. Steps are stored by index: append new steps, never insert or reorder; a released step whose notes change goes into `CHANGED_STEPS` (`course/progress.js`, next `rev`), which drops its old records once. A step on an exercise with a subdivision selector carries `sub` (the self-test checks it). The self-test checks every step. See README "Adding a course lesson".
- Numbers (user, 2026-10-28: "hotel numbering", replacing the 2026-10-15 running numbers): an exercise's number is its level, then two digits (305 = Level 3), fixed in `curriculum/numbers.js` and kept for good; a new exercise takes the next free number of its level (the self-test names it), a removed one's number goes to `RETIRED` and is never reused. The Library orders by level, topic (PATH_ORDER) and the module's `export default [...]` list (`t.order`), not by number. A lesson's number is its stage, then its own number there ("3.15"), fixed in `course/numbers.js` the same way (`RETIRED_LESSONS`); units are named, not numbered; a checkpoint shows ◆ (QA round 20: a ✓ beside its status read as done), a test ★. Everything stored uses ids, never numbers. Exercise and lesson numbers quoted elsewhere in this file from before 2026-10-28 are the old running numbers. Both lists are renumbered once in course order just before the launch, then frozen (LAUNCH-TODO.md).
- `web/js/version.js` is overwritten by CI with the release number (`1.0.<run number>`) and commit, shown at the bottom of Settings. Keep the committed copy empty (it reads "development version" locally).
- Sound: CC0 Karoryfer "darkblack" bass samples in `web/audio/bass/` (B0–E4, plus ghost notes); `web/js/audio.js` falls back to a synth.
- Design: navy/teal/periwinkle/peach palette (no brown fretboard), real string-gauge proportions, root markers drawn as rounded squares. Keep this look.
- Downloading anything new (samples, packages, SDKs) needs the user's explicit OK first.
- Practice log and backup (user, 2026-10-23, roadmap phase 1): `web/js/practiceLog.js` counts the minutes the player plays, per local day (`bassclass.log.v1`; a run with no touch or key for 20 minutes stops counting), and it is Home's headline (`ui/practiceCard.js`; user, 2026-10-23: "on top, colourful, clearer"): a ring for today against the session length (the daily goal, 15–60′; gold once met), the last 7 days' total and days practised (🔥 days in a row from 2), and the 7 days as bars with their minutes (gold where the goal was met, a dashed 🎯 goal line); the days scroll sideways back to the first day logged (14 days at least, 90 at most), today at the right; a tap on a day or the ring opens a bubble beside it (`bubbleOnTap`/`showBubble` in `ui/dom.js`, the ⓘ bubble's code), not a toast at the bottom (user, 2026-10-23). `web/js/backup.js` saves every `bassclass.*` record to one JSON file (Settings → Backup) and loads one back (it replaces them all, then reloads). In the APK, saving goes through `BassClassNative.saveFile` (Android's "Save to" picker, answered by a `bassclass-saved` event) and loading through the WebView's file chooser. Every stored key starts with `bassclass.`, so backups carry it.
- Mastery, one record of progress everywhere (user, 2026-10-26: "the checks have to be extensive to all the app regardless in what section it has been achieved"; `web/js/mastery.js`): an exercise is mastered (the Library's ✓ mastered, `done` in `bassclass.progress.v1`) when a full loop reached its goal and the player ticked it, wherever: in the Library or today's session (✓ Mastered under ⋯, which until then says "🎯 To master it: a full loop at 92 BPM in 8ths"; a loop that reaches the goal stores `met` and says so), or in a lesson (a step at least as hard as the goal, passed and ✓ Clean, masters it at once). Its goal (`goalOf`) is the hardest of its steps in its own level's stage (tempo × notes per beat; every exercise has steps there); ear rounds without a goal need one full loop. Both ways: a mastered exercise passes and cleans the course's steps on it whose goal is no harder (`masteryCovers`, worked out on the fly, so unmastering takes it back), and lessons it completes get their completion day and reviews (`onMastery` in `course/progress.js`; records made once on load for exercises mastered before). A Library level 80% mastered (`LEVEL_PASS`) counts as known in the course (`isKnown`): My level moves on, Continue skips its unfinished lessons, and they come back as reviews. Library cards show "🎯 92" until mastered; the Library ⓘ explains both rules. Exercises mastered before this rule (any tempo) stay mastered. A level passed is measured against the number of exercises it had then (`bassclass.levels.v1`), so exercises an update adds never take it back (QA round 20); unmastering below 80% of that count does.
- Jazz licks (`curriculum/licks.js`) are ORIGINAL phrases in standard jazz vocabulary, notated in C (or C minor) and transposed. Never paste note-for-note transcriptions of copyrighted recorded solos.
- "New" chips (user, 2026-10-28: "each time we add something new we need a chip on top, like the Pro one, telling 'new', that will disappear after being used once"; `web/js/news.js`, `bassclass.new.v1`): nothing to date by hand. Each start records the content ids it knows (exercises `ex:`, lessons `lesson:`, drum patterns `style:`, progressions `prog:`, sounds `sound:`); whatever an update adds is new for that player until used once (an exercise or lesson opened, a pattern or progression picked, a sound chosen). A first start knows everything, so a new player sees none. The chip (`newChip` in `ui/screens.js`, the app's teal beside the gold Pro) sits on Library cards, map lesson rows, picker cards (a dot on a group holding new cards) and the room's sound buttons; a Library level and a map stage show "3 new". New content needs no extra step: add it to its data and it is new for every player who updates. A Pro item tapped (its Pro sheet opened) counts as used, so a free player's chips go too (QA round 20); a lesson's step played from the session or a link uses its lesson; a backup without the record keeps the device's. The drone's Change shows New (`drone:picker`) until its picker is first opened; its cards keep their own chips. - Chords and harmonics from the user's reference docs (user, 2026-10-28: "more chords exercises to learn harmony", "harmonics with correct tone spelling", "harmonics finger position (not always in the middle of the fret)", "represent harmonics like triangles"): new chord types `add9`, `maj69` (6/9), `min69` (m6/9), `maj7sus4`, `dom11`, `min11`, `min13` in `theory.js` CHORDS; `hm-chord-formulas` (Level 3, free: every type of a family on one root, up its formula and back, textbook spelling: triads and sus, 6ths and added 9ths, 7th chords, 9ths/11ths/13ths; lesson `chord-formulas` appended to "7th chords in the key", Stage 3, with a checkpoint line). The phone profile cuts below 350 Hz (`PHONE_HP`, 200 before): 80% of the energy lay under 400 Hz, which a phone speaker cannot play but which drives its cone into distortion; now 5 dB less there, and with that headroom the bass sounds 0.4 dB louder on the phone than before (A-weighted).
